# Earlier SakAccounts data and feature migration

The separate `SAK-Accounts` project contains the earlier FastAPI bookkeeping application. It had businesses, vendors, inventory, documents, bank accounts, detailed transactions, statement and Amazon imports, and reports. Its local SQLite database and former VPS SQLite database diverged. The older project's configured Supabase hostname did not resolve during this installation, so it could not be inspected as an additional source.

The owner selected the former VPS SQLite database as the primary source. Its April 2026 snapshot has 4,691 transactions, 19 bank accounts, 313 inventory items, and 246 vendors. The local snapshot has 5,034 transactions. Their transaction IDs overlap for 3,861 records, while 830 are unique to the VPS and 1,173 are unique to the local copy. Shared IDs also have different payloads. Both versions are preserved with source labels and SHA-256 checksums in `sakaccounts.legacy_snapshot_records`, protected by owner-only RLS. The `legacy_primary_transactions` and `legacy_primary_accounts` views expose the selected VPS data read-only to the owner.

The `legacy_source_divergence` flag remains unresolved. Opening balances and historical transactions are archived intact but have not been posted into the new event ledger. The dashboard marks its balance as pending reconciliation. This prevents a zero or partial balance from being mistaken for a verified opening figure.

To finish the functional migration, compare local-only and changed records with the VPS primary records, resolve the flag with source references, then map the approved opening figures and transactions into the new model. Retain the original IDs and import provenance, avoid double posting, and reconcile totals by business and account before making migrated balances final. The richer features of the earlier application still need implementation or integration against this Supabase project; the current dashboard provides owner login, basic posting, accounts, and read-only recent history.
